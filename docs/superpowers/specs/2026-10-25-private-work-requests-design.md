# Private work requests — approved design

User approved private reader-to-administration requests and instructed implementation on 2026-10-25. Preserve the current catalog, accounts, editorial publishing and PDF system. No mock cleanup or real publication.

## Product flow
- `/requests/new`: verified signed-in reader enters title (2–150 chars), category manga/manhwa/novel/comic, optional HTTP(S) reference URL (max2048) and message (max1000). Show up to8 matching already-public library works before submission, never other readers' requests. Preserve form on failures, use stable submission UUID across uncertain retries, and navigate to the persisted own request on success.
- `/requests` and `/requests/[id]`: only the current user's submitted requests, own original text, private administration reply, shared status note and an available-work link. Never expose other requesters, their messages, internal notes or merge IDs. Guest login returns to the intended request page.
- Discovery exposes “اطلب عملًا”, with searched title prefilled in empty search results; account navigation exposes “طلباتي”. Keep existing RTL charcoal/violet visual language and accessible44px controls.
- `/admin/requests` and `/admin/requests/[id]`: admin only. Paginated/searchable/filterable root request groups, new count, distinct interested reader count, group status, per-member private reply/internal note, explicit merge destination selection. Merging preserves original submissions/replies and adopts the displayed destination status. No public voting or chat subsystem.
- States `new`, `reviewing`, `preparing`, `available`, `declined`. Available requires an actually public series with a live chapter. Public-link eligibility is checked again when reading, so withdrawal never exposes a draft or leaves a usable private link.

## Data/behavior
One additive ContentRequest table: original request owner/title/category/reference/message; conservative normalized title and client submission ID; own private reply/internal note; group status/statusNote/fulfilledSeriesId; flat self-relation mergedIntoId and version counter. Unique owner+submission ID and owner+category+normalized title prevent double-click/retry and exact repeated requests. Normalization folds Unicode/case/whitespace only; no fuzzy automatic cross-reader merge. Keep the first saved original text on duplicate, return its own ID.

Each submission initially forms its own group. Admin merges only distinct same-category roots, never an available group, flattening descendants in one serializable transaction. Maximum200 original submissions per group bounds fan-out/detail loading. Reader status uses its canonical root; reader reply is always its own original row's reply, never the root owner's personal reply. Distinct interested-reader count deduplicates owners after merge.

New requests: maximum3 persisted requests per rolling24h per active verified account, plus bounded submit-attempt throttling using existing rate-limit infrastructure. Auth/roles are rechecked inside mutations; versions reject stale competing edits. Only admin can reply/change/merge. Admin response to one member notifies that owner only; group status updates notify distinct owners with links to their own request. Internal notes never generate reader messages. Repeated no-op writes do not resend notifications. Store state and notifications in the same transaction. New request notifies active verified admins. Use existing `system` notifications; no SMTP/external mail, attachments, new paid infrastructure or arbitrary URL fetching.

Safe same-origin POST route boundary uses `X-Bunny-Request:1`; reject cross-origin mutations, malformed input and unsafe links. Private endpoints/pages must not cache personalized data publicly. Pagination uses20 groups per page; catalog suggestions bounded8. Own request lists can cap50 with explicit pagination/total rather than silently dropping older requests.
