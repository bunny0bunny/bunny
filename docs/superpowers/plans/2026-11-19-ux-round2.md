## Phase R — reader and profile (first)

### R1. Profile picture and name  · schema

Today a reader's "picture" is the first letter of their name on one of four tinted circles, or the site logo (`src/components/accounts/account-avatar.tsx`). Comments ignore it and always draw the initial (`comments-section.tsx`). Names are free text with no rules.

1. **Name.** Keep free text (the reader types what they want, 2-40 chars). Add server-side rules in one place (`src/lib/profile-name.ts`), used by register, profile settings and onboarding:
   - trim and collapse whitespace; reject control/zero-width/bidi-override characters;
   - reserved words, after Arabic normalization (`arabic-search.ts` normalizer) and case folding: بانيورا, باني, إدارة/الإدارة, مشرف, admin, moderator, bunyora, bunny, support, دعم. Reject when the normalized name equals or starts with one of them. Staff badges already show the real role, so staff do not need these words in their names.
   - No uniqueness requirement (comments show the avatar + name; uniqueness would push people to "name123").
2. **Preset avatars.** Replace the four colour seeds with a set of illustrated avatars in `public/avatars/` (square WebP or SVG, ≤20 KB each, 256 px). Registry `src/lib/avatars.ts`: `{ id, src, labelAr }[]`. `avatarSeed` stays a string; old seeds (`initials`, `violet`, `teal`, `gold`, `bunny`, `v1`) keep rendering as today so nothing breaks. The picker becomes a radio grid of images (fieldset/legend, 44 px targets) with no colour-name labels.
   - **Open decision for the owner:** art source. Option A: Claude draws ~16 vector bunny-mascot avatars (colour, accessories, reading poses) now; commissioned art can replace the files later without code changes. Option B: wait for commissioned manga-style art.
3. **Upload own picture.** Add `Profile.avatarKey String?` (migration). Mirror the team-logo pipeline that already exists (`src/lib/public-identities/avatar.ts`, `avatar-policy.ts`, `avatar-editor.tsx`):
   - client crops to a square 512 px WebP (reuse `IdentityAvatarEditor`);
   - `PUT/DELETE /api/profile-avatar` for the signed-in user only; same checks as identities: trusted Origin + custom header, `MEDIA_UPLOADS_ENABLED`, ≤256 KB, sniffed WebP, square, ≤512 px, 10 uploads/hour rate limit, serializable re-check after storage, delete old object after commit, audit row;
   - `GET /api/profile-avatars/[profileId]/[file]` serves only the current key, `Cache-Control: public, max-age=31536000, immutable` (file name is a random UUID), 404 when the account is disabled;
   - key `media/<prefix>/profiles-<profileId>/<uuid>.webp`;
   - admins can remove any profile picture from `/admin/users` (moderation), audited;
   - account deletion (when it exists) and the media maintenance cron must delete the object; add the prefix to the orphan sweep in `src/lib/media/**`.
   - **Question for review:** is serving user-uploaded avatars publicly (no auth) acceptable, given team logos already are?
4. **One avatar component everywhere.** `ProfileAvatar({ seed, avatarPath, name })` replaces `AccountAvatar` call sites and the hard-coded initials in comments, the header menu, `/admin/users`, moderation and the profile page. Queries that return comment authors add `avatarKey` and map it to `avatarPath` server-side.
5. **Onboarding.** `/welcome` gets a first step "اختر اسمك وصورتك" (name prefilled, preset grid, upload button), then the existing genre step. Both skippable.

Tests: name rules (unit); avatar upload/remove/authorization/size/type/rate-limit (DB suite, modelled on `identity-avatars.test.ts`); comment author carries `avatarPath`.

### R2. "Continue reading" and guest progress

1. When the latest progress for a work is completed, "continue" points to the next readable chapter ("الفصل التالي"), and the home hero keeps the work if a newer chapter exists. Files: `work-hero-actions.tsx`, `series/[slug]/page.tsx` server progress query, `queries.ts#getContinueReading` (also fix `take: 3` before de-duplicating by work).
2. Guest progress merge: after sign-in/registration, the client posts the local entries (`progress-local.ts`) to a `mergeGuestProgress` action, which upserts per chapter keeping the newer `updatedAt`, max 200 entries, only live chapters. Then the local mirror is cleared.
3. Clear (or namespace by profile id) the local mirror on sign-out so the next person on the device does not see it.
4. Guests: chapters below the saved chapter show as read in the chapter list.

Tests: merge keeps newer, ignores deleted/unpublished chapters, is idempotent; next-chapter selection with decimal chapter numbers.

### R3. Use the genres readers pick

`preferredGenresJson` is saved at onboarding and never read. Add a home rail "لأنك تحب: …" from those genres (falls back to nothing when empty), and an editor for them in profile settings. No schema change.

### R4. Content requests: withdraw and edit  · schema

1. `ContentRequest.withdrawnAt DateTime?`. Owner action `withdrawContentRequest` (POST `/api/content-requests/[id]/withdraw`) allowed in `new`, `reviewing`, `declined`; refused in `preparing`/`available`. Merged members can be withdrawn; a group root with members is hidden for its owner but stays for admins. Withdrawn rows still count in the 3-per-24h quota; admin `requesterCount` recounts.
2. Edit title/category/message/link while `new` and not merged, guarded by `version`.
3. Duplicate submit: show «لديك طلب سابق لهذا العمل» on the destination; withdrawn rows are excluded from the duplicate check (partial unique index `WHERE "withdrawnAt" IS NULL` replaces `@@unique([profileId, category, normalizedTitle])` — **question for review:** safest way to swap this constraint on a live table).
4. Show remaining requests (n of 3) on `/requests/new`.

- Notifications: per-item delete and "clear read"; rows without a link get a "mark read" button; like notifications link to the chapter.

## Phase C — translator / contributor flows

### C1. Opening a chapter must not create a draft
`/studio/chapters/[id]` calls `openOrCreateDraft` on every load, which forks a new draft from a published or withdrawn revision (`editorial.ts` `openOrCreateDraft`). Change: page load uses a read-only `getWorkingRevision` (latest pending revision, else latest revision read-only). The editor shows published/withdrawn revisions read-only with a «إنشاء نسخة جديدة للتعديل» button that calls `openOrCreateDraft`. Existing behaviour for pending revisions is unchanged.

### C2. Editing during review
`updateDraftSnapshot` silently moves `review` back to `draft`. Change: while a revision is in `review`, the editor shows "تعديل هذه النسخة سيسحبها من المراجعة" and requires confirmation; add explicit `withdrawFromReview` (audited, notifies assigned editors). Server keeps accepting the save only with `confirmLeaveReview: true` for `review` revisions.

### C3. Show what the reviewer asked for
In `changes_requested`, show a banner above the editor with the latest return reason, reviewer name and time (from `ChapterEditorialEvent.reasonAr`).

### C4. Notify the right person
Approve, recommend and return notify the submitter (actor of the latest `submit` event) in addition to today's audience; return goes to the submitter and editors, not every contributor on the work. Text names the work and chapter number (the generic wording at `editorial-notifications.ts:50` was to avoid leaking unpublished titles to readers; staff-only notifications can name them — **question for review**).

### C5. One home for contributors: `/studio`
- Default filter = actionable (draft, changes_requested, review); add "mine" (from editorial events), work filter, withdrawn tab, "آخر تعديل منذ …", sort by latest revision `updatedAt`, pagination (50).
- "أعمالي" cards with «فصل جديد لهذا العمل» → `/admin/chapters/new?series=`.
- Empty state for no assignments: «لم تُسند إليك أعمال بعد. ستظهر هنا عندما تضيفك الإدارة إلى عمل.»
- Show the team(s) credited on assigned works, with an edit link for the team owner.
- For contributors: account menu item «استوديو الفريق» instead of «لوحة الإدارة»; hide `/admin/chapters` from their nav (route stays, server checks unchanged).

### C6. Invitation landing
New accounts get `next=/studio` after accepting; staff skip the reader genre step (they can do it later from settings).

### C7. Chapter number helper
On `/admin/chapters/new`, list the existing numbers for the chosen work, including drafts in progress by others, and warn before submit if the number is taken.

### C8. Page editing for PDF chapters (from audit task 7)
Allow delete/reorder of imported pages in a new revision (pagesJson edit; assets stay owned by the chapter), and "replace page N" with one uploaded image through the existing `putPage` path. Image/ZIP chapter upload and tall-webtoon splitting are a separate plan after this round.
